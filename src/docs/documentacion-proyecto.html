1. Resumen en una página

Mundo Burguer es la web de un restaurante de Moriles (Córdoba). Tiene dos caras:

  • La web pública (/, /carta, /sobre-nosotros, /contacto y las páginas legales). Es informativa: enseña la carta, la historia del local, los datos de contacto y el mapa. Cualquiera puede verla.
  • El panel privado (/panel). Es un pequeño gestor de contenidos para editar la carta sin tocar código: crear/editar/ocultar productos y categorías, gestionar el bloque «Configura tu menú», elegir los destacados de la portada y aprobar quién puede entrar. Solo entran dos personas, identificándose con su cuenta de Google.

La tecnología, en dos frases:

  • Frontend: una aplicación de una sola página (SPA) hecha con React 19 + TypeScript y empaquetada con Vite 8. Al compilar (pnpm build) genera una carpeta dist/ con archivos estáticos (HTML, JavaScript, CSS, imágenes). Esa carpeta se sube a un hosting de estáticos / CDN (recomendado: Vercel, pero vale Netlify, Cloudflare Pages o un nginx propio). No hay servidor propio de la aplicación.
  • Backend: Supabase, un servicio gestionado que reúne una base de datos PostgreSQL, el sistema de login (con Google), almacenamiento de ficheros (las fotos de los productos) y una API REST automática sobre la base de datos (PostgREST). La autorización de verdad (quién puede leer o escribir qué) la aplica PostgreSQL con reglas RLS (Row Level Security). El frontend nunca es la barrera de seguridad.

Idea clave que se repite en todo el documento: el navegador descarga «claves públicas» de Supabase (la anon key). Eso es normal y seguro siempre que las reglas RLS estén bien escritas, porque son ellas —y no el código de React— las que impiden que un desconocido lea datos ocultos o modifique la carta.

2. Vocabulario mínimo (glosario rápido)

Si algún término del documento no te suena, búscalo aquí. Al final hay un glosario más completo.

Término Qué significa aquí
SPA (Single Page Application) La web es un único documento HTML; al navegar entre secciones no se recarga la página, el JavaScript intercambia el contenido. Da sensación de aplicación.
Build / compilar Convertir el código fuente (carpeta src/) en archivos listos para el navegador (carpeta dist/). Se hace con pnpm build.
Hosting estático / CDN Servidor que solo entrega ficheros ya hechos (no ejecuta código de servidor). Una CDN además los replica por el mundo para que carguen rápido. Aquí: Vercel.
Supabase El «backend en una caja»: base de datos PostgreSQL + login + almacenamiento + API REST, todo gestionado por ellos.
PostgREST Componente de Supabase que expone automáticamente la base de datos como una API REST en /rest/v1/….
RLS (Row Level Security) Reglas dentro de PostgreSQL que deciden, fila por fila, quién puede leer o escribir. Es la seguridad real del proyecto.
anon key Clave pública de Supabase que va en el navegador. Identifica a un visitante «anónimo». No da permisos por sí sola: RLS filtra lo que ese rol puede ver.
service_role key Clave secreta que se salta RLS. Nunca va al navegador ni al repositorio. Solo se usa desde tu ordenador para el seed inicial.
Migración Un archivo .sql con cambios en la base de datos (crear tabla, añadir columna…). Se aplican en orden y no se reescriben una vez aplicados.
Snapshot de la carta Copia de la carta en un JSON incluido en el build (menu.snapshot.json). Sirve para que la web funcione aunque el backend no responda.
Preview / Production deployment En Vercel/Netlify: cada rama de Git genera una URL de preview (pruebas) automática; la rama principal (main) genera la production (el dominio real).

3. Arquitectura general: frontend, backend, dónde vive cada cosa

▲ despliega automáticamente al hacer git push ▲
3 · Repositorio Git (GitHub) El código fuente. Cuando subes cambios, Vercel ejecuta pnpm build y publica el resultado.
  — y en paralelo, desde el navegador (pieza 1) —
▼   HTTPS / WebSocket (datos y login)   ▼
4 · Supabase (backend gestionado, proyecto aparte)
PostgreSQL Tablas + reglas RLS. El corazón de los datos.
PostgREST /rest/v1/… — API REST automática de la BD.

Storage Bucket menu: fotos de los productos, lectura pública.
▼   (solo durante el login)   ▼
Google Cloud — cliente OAuth Solo conoce una URL: el callback de Supabase (https://<ref>.supabase.co/auth/v1/callback). No sabe nada de tus dominios.
Google Analytics 4 (opcional) Solo se carga en el navegador si la persona acepta la cookie de «Análisis». Si VITE_GA_MEASUREMENT_ID está vacío, no se carga nunca.

3.2. ¿Dónde se aloja cada cosa y cómo se despliega?

Pieza Dónde vive Cómo se despliega / actualiza
Frontend (la web) Hosting estático + CDN. Recomendado Vercel. Alternativas sin cambiar código: Netlify, Cloudflare Pages, nginx/Apache propios. Conectas el repo de GitHub al hosting. Cada git push dispara pnpm build en el hosting y publica dist/. No subes archivos a mano.
Backend (base de datos, login, storage) Un proyecto de Supabase (su nube, región europea recomendada). Es totalmente independiente del hosting del frontend. Los cambios de esquema se aplican con migraciones SQL (supabase db push o pegando el SQL en el editor del panel de Supabase). Los datos de la carta se editan desde /panel.
Dominio Un registrador de dominios (donde lo compres). Los DNS apuntan al hosting del frontend. Se configura una vez: registros DNS hacia Vercel + el dominio dado de alta en el panel de Vercel y en Supabase (Site URL / Redirect URLs).
Identidad de Google Un proyecto en Google Cloud Console con un «ID de cliente OAuth». Se configura una vez. Solo se le da la URL de callback de Supabase. No cambia al cambiar de dominio.

Por qué está partido así: el frontend es «tonto» (solo ficheros) y se puede mover de hosting en minutos. El backend concentra los datos y la seguridad. Si mañana quieres cambiar Vercel por Cloudflare Pages, el backend ni se entera.

La cadena de arranque es corta y siempre la misma:

       └─ src/app/App.tsx  <Providers> + <RouterProvider>
            ├─ src/app/providers.tsx
            │     MotionConfig (respeta "reducir movimiento" del sistema)
            │     CookieConsentProvider (banner de cookies + Google Analytics
            │       gateado por consentimiento)

Detalle importante de diseño: el proveedor de sesión (AuthProvider, que usa el SDK de Supabase) no está en providers.tsx. Vive dentro del árbol de rutas privadas (src/features/auth/PrivateArea.tsx). Así el SDK de Supabase queda en el «trozo» (chunk) de /panel y la web pública no lo descarga.

4.4. Estrategia de datos de la carta (memoria + caché + snapshot)

La carta pública necesita cargar rápido y no romperse nunca. El módulo src/features/menu/data/menuStore.ts implementa un patrón SWR («muestra lo que tengas, revalida por detrás») con tres niveles de respaldo:

  1. Memoria (variable del módulo): lo más rápido, dura lo que dure la pestaña abierta.
  2. localStorage (clave mb.menu.v4): lo que se trajo del backend en visitas anteriores. Sobrevive a recargas.
  3. Snapshot incluido en el build (src/features/menu/data/menu.snapshot.json): último recurso si el backend no responde y no hay nada en caché. La web siempre enseña algo.

Reglas de refresco:

  • En cada carga de página se revalida contra el backend (por eso un cambio hecho en el panel se ve recargando una vez).
  • Dentro de la misma sesión, al navegar entre vistas de la SPA, solo se vuelve a pedir si el dato tiene más de 20 segundos (evita ráfagas de peticiones).
  • Si la petición falla, se devuelve la caché o el snapshot sin propagar el error y sin bucles de reintento.

El hook que consumen las vistas es src/features/menu/hooks/useMenuData.ts. Expone products, categories, menuConfig y un indicador stale (datos viejos mientras revalida).

4.5. Cómo se parte el código (bundle y carga diferida)

En vite.config.ts se definen «trozos» (chunks) para que el primer acceso descargue lo justo:

  • react-vendor: react, react-dom y react-router.
  • motion: framer-motion.
  • Cada ruta lazy es su propio trozo: la web pública no descarga el código del panel, y el panel no descarga hasta que entras.
  • El SDK @supabase/supabase-js queda solo en el trozo de /panel porque AuthProvider se monta ahí. La lectura pública de la carta usa fetch a pelo (ver apartado 6), sin SDK.

Todas están en el esquema public. Resumen funcional:

5.3. Seguridad a nivel de fila (RLS)

Todas las tablas tienen RLS activado. El modelo (migración 0005 y posteriores):

  • Lectura pública (rol anon) de categories, products, menu_config_* y product_config_groups: solo filas no borradas y, en productos, con visible = true.
  • Personal aprobado (is_approved_staff() → admin o editor): lee todo (incluidos ocultos) y puede insert/update.
  • Borrado físico: no se concede a nadie por la API. El panel hace borrado lógico (rellena deleted_at). Purgar de verdad = SQL con service_role.
  • profiles: cada usuario lee su fila; el admin (is_admin()) lee y modifica todas.
  • audit_log: solo lo lee el admin.
  • Storage (bucket menu): lectura pública; subir, reemplazar y borrar objetos solo el personal aprobado.

Las funciones is_admin() e is_approved_staff() son SECURITY DEFINER: consultan profiles saltándose RLS para no entrar en recursión con las propias políticas de esa tabla.

5.4. Funciones, triggers y RPC

NombreTipoQué hace
handle_new_user() Trigger sobre auth.users (alta) Al crearse una cuenta de Google, crea su fila en profiles. Si el email está en bootstrap_admins, entra approved; si no, pending.
ensure_profile() RPC (la llama el frontend tras el login) Devuelve el perfil del usuario; lo crea al vuelo si el trigger anterior no llegó a existir. Es la red de seguridad.
is_admin() / is_approved_staff() Funciones SECURITY DEFINER Las usan las políticas RLS para decidir permisos.
set_updated_at() Trigger (varias tablas) Mantiene la columna updated_at al día.
validate_product_price_shapes() Trigger sobre products Valida la forma de variants/tiers (lo que un CHECK simple no puede).
guard_category_delete() Trigger sobre categories Impide borrar (lógicamente) una categoría que aún tiene productos activos.
guard_profiles_admin_safety() Trigger sobre profiles (0017) No te deja cambiarte a ti mismo el estado/rol, y no deja degradar al último administrador («Debe quedar al menos un administrador aprobado»).
touch_last_seen() RPC (0018) Pone last_seen_at = now() para el usuario actual. El panel la llama cada 2 minutos y al cerrar sesión, para saber la «hora de última desconexión».
write_audit('...') Triggers de auditoría Escriben en audit_log los cambios de la carta.

5.5. Storage (imágenes de producto)

  • Bucket menu, público para lectura. Las URLs son del tipo https://<ref>.supabase.co/storage/v1/object/public/menu/<archivo>.
  • El panel recorta y comprime la imagen en el navegador antes de subir (a WebP), por eso el bucket limita el tipo y el tamaño (la migración 0011 amplió los límites: webp/jpeg/png ≤ 5 MB).
  • Subir / reemplazar / borrar: solo personal aprobado (RLS de Storage).

5.6. Autenticación con Google, paso a paso

  1. En /acceso pulsas «Entrar con Google». El frontend llama a signInWithOAuth({ provider: 'google', options: { redirectTo: `${origin}/acceso` } }) con flujo PKCE.
  2. El navegador va a Google. Google, al terminar, vuelve al callback de Supabase (https://<ref>.supabase.co/auth/v1/callback) — la única URL que conoce Google Cloud.
  3. Supabase valida, crea/actualiza la fila en auth.users (dispara handle_new_user) y redirige de vuelta a tu app, a la URL que pusiste en redirectTo (/acceso). Qué URLs de tu app están permitidas se configura en Supabase → Authentication → URL Configuration (Site URL + Redirect URLs), no en Google.
  4. Ya en /acceso, el SDK detecta la sesión en la URL (detectSessionInUrl), la guarda y emite onAuthStateChange('SIGNED_IN').
  5. AuthProvider llama a la RPC ensure_profile y obtiene status + role. resolveAccess() traduce eso a: ready (entras), pending (a la espera de que el admin decida), denied (rechazado) o anonymous.
  6. Si ready, <RequireAccess> deja ver /panel.

Cierre por inactividad: AuthProvider cierra la sesión tras 15 minutos sin interacción en la parte privada. El contador se comparte entre pestañas con localStorage (clave mb.panel.lastActivity).

6. Cómo se comunican el frontend y el backend

6.1. Dos caminos distintos, a propósito

Carta pública Panel privado
Quién Cualquier visitante (rol anon). Usuario con sesión (rol authenticated).
Cómo fetch() «a pelo» a ${SUPABASE_URL}/rest/v1/… con la anon key en las cabeceras. Sin SDK. (src/features/menu/api/menuApi.ts) @supabase/supabase-js (cliente único y perezoso en src/lib/supabase.ts), que añade el token JWT a cada petición.
Por qué Para no meter el SDK (~pesado) en el bundle que descarga todo el mundo. La carta es solo lectura. Necesita login, refresco de token, escritura y subida a Storage: el SDK lo resuelve.
Qué protege los datos En ambos casos, RLS en PostgreSQL. El anon solo ve lo visible/no borrado; el authenticated aprobado ve y escribe todo. El frontend no es la barrera.

6.2. Qué pide exactamente la carta pública

fetchMenu() lanza 5 lecturas en paralelo a PostgREST: categories, products (con su categoría y sus product_config_groups anidados), menu_config_meta, menu_config_groups y menu_config_items. Luego los «mappers» (src/features/menu/api/mappers.ts) transforman las filas de la BD al formato que usa la interfaz, y compone la URL de cada imagen a partir de image_path + la base pública de Storage.

Si VITE_SUPABASE_URL/VITE_SUPABASE_ANON_KEY no están definidas, menuBackendConfigured es false y la web tira directamente del snapshot: sigue funcionando.

7. Seguridad del sistema

7.1. Qué se protege y qué se asume

(Detalle completo en SECURITY.md.) Lo que se protege es la capacidad de editar la carta. Solo hay dos cuentas con acceso. Asunciones aceptadas: la anon key es pública; la carta publicada es información no sensible; el panel no maneja pagos ni datos personales de clientes.

7.2. Claves y variables de entorno

Variable¿Pública?Dónde va
VITE_SUPABASE_URL Sí (viaja en el bundle) Panel del hosting (Vercel) como variable de entorno.
VITE_SUPABASE_ANON_KEY Sí Ídem. Su seguridad no depende del secreto, sino de RLS.
VITE_SITE_URL Sí Ídem. Se usa para canonical, Open Graph y el sitemap.
VITE_GA_MEASUREMENT_ID Sí Ídem. Vacía = no se carga Google Analytics.
SUPABASE_SERVICE_ROLE_KEY NO — secreta Solo en tu .env.local (ignorado por git), solo para pnpm seed. Nunca en Vercel, nunca en el repo.

El prefijo VITE_ es lo que hace que Vite incluya la variable en el bundle. Cualquier cosa sin ese prefijo no llega al navegador.

7.3. Cabeceras de seguridad HTTP

Se definen por hosting, no en el código de la app, para no atarla a ninguno. Están duplicadas —idénticas— en dos ficheros:

  • public/_headers → lo leen Netlify y Cloudflare Pages.
  • vercel.json (clave headers) → lo lee Vercel.

Un test (src/test/security-headers.test.ts) falla si los dos ficheros divergen, para que nunca se olvide actualizar uno. Cabeceras aplicadas a todas las respuestas: Content-Security-Policy, Strict-Transport-Security (HSTS 1 año), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy (bloquea cámara, micro, geoloc., pagos, USB). La CSP usa el comodín https://*.supabase.co, así que no hay que tocarla al cambiar de proyecto de Supabase. Desglose directiva a directiva en DEPLOY.md.

7.4. Flujo de solicitudes de acceso

No hay lista blanca en código. Cualquier cuenta de Google puede intentar entrar: queda pending con el mensaje de que «el administrador de la web decidirá si su solicitud de registro es válida». Desde /panel/solicitudes el admin aprueba (y asigna rol) o deniega; desde /panel/accesos puede cambiar roles, revocar o reactivar, y ver la «última desconexión» de cada persona (menos la suya).

7.5. Discreción del panel

  • Acceso solo por un icono de candado pequeño en el pie; rutas /acceso y /panel.
  • Ambas rutas con noindex, en Disallow de public/robots.txt y excluidas del sitemap.xml.
  • La analítica no registra páginas privadas (PRIVATE_PREFIXES en Layout.tsx).

10. Despliegue: cómo se publica la web

10.1. Lo mínimo para poner esto en internet

  1. Un proyecto de Supabase creado (región europea). Aplica las migraciones 0001–0018 en orden. Copia su URL y su anon key (Project Settings → API).
  2. Un proyecto en Google Cloud con un ID de cliente OAuth. En «Authorized redirect URIs» pon solo https://<ref>.supabase.co/auth/v1/callback. Pega el Client ID y Client Secret en Supabase → Authentication → Providers → Google.
  3. Una cuenta de hosting (Vercel). Conecta el repositorio de GitHub. Framework preset: Vite. Build command: pnpm build. Output: dist/.
  4. Variables de entorno en el hosting: VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_SITE_URL, y opcionalmente VITE_GA_MEASUREMENT_ID.
  5. El dominio: cómpralo, y en tu registrador crea los registros DNS que te indique Vercel (normalmente un A / ALIAS para el dominio raíz y un CNAME para www). Da de alta el dominio en el panel de Vercel.
  6. Supabase → Authentication → URL Configuration: pon el Site URL = https://www.tudominio.es y añade en Redirect URLs todas las URLs desde las que se hará login (dominio real, www, la de pruebas, y http://localhost:5173 para desarrollo).

Recordatorio del proyecto: el Site URL de Supabase está ahora en una IP/URL temporal de pruebas. Hay que cambiarlo al dominio real cuando lo compres, o el login redirigirá al sitio equivocado.

10.2. El «SPA fallback» (por qué hace falta)

Al ser una SPA, si alguien entra directo a https://tudominio.es/carta/mi-burger, el hosting debe servir index.html (y que React Router resuelva la ruta), no devolver un 404. Eso ya está resuelto: vercel.json → rewrites (Vercel); public/_headers/_redirects o el ajuste «SPA» (Netlify / Cloudflare); try_files $uri /index.html (nginx).

10.3. Qué NO cambia al cambiar de hosting

  • El código de la app (no hay APIs propias de Vercel).
  • El backend de Supabase.
  • La configuración de Google Cloud.
  • La CSP (usa comodín *.supabase.co). Solo se toca si añades otro servicio externo.

11. Tu pregunta: entorno de pruebas + producción automática con el dominio real

«Cuando compre el dominio y ponga esto en producción para que todo el mundo pueda acceder, ¿cómo puedo desplegarlo en un servidor de pruebas mientras voy haciendo mejoras, y que solo cuando tenga esas mejoras acabadas haga un build a producción y automáticamente se actualice la web del dominio real?»

11.1. Respuesta corta

No montes ni gestiones tú ningún servidor. Usa lo que Vercel (o Netlify, o Cloudflare Pages) ya hace solo: despliegue continuo basado en ramas de Git.

  • La rama main del repositorio = producción → se publica sola en tu dominio real cada vez que algo llega a main.
  • Cualquier otra rama = entorno de pruebas → Vercel le da una URL de preview automática, con su propio build, sin tocar producción.
  • Tú trabajas en una rama, la pruebas en su URL de preview, y cuando está lista la fusionas a main. Ese merge dispara el build de producción y actualiza el dominio real. Cero pasos manuales.

11.2. Montarlo, una sola vez

  1. Repositorio en GitHub con la rama main como principal.
  2. Importa el repo en Vercel. Por defecto ya asigna:
    • Production = rama main. Aquí conectas tu dominio real (tudominio.es y www).
    • Preview = todas las demás ramas y cada Pull Request. URL del tipo mundoburguer-git-<rama>-<cuenta>.vercel.app.
  3. (Opcional pero recomendable) Una URL de pruebas fija. Crea una rama estable, p. ej. staging, y en Vercel → Settings → Domains asígnale un subdominio: staging.tudominio.es (un CNAME en tu registrador hacia Vercel). Así siempre pruebas en la misma dirección, fácil de recordar y de enseñar a otra persona.
  4. Variables de entorno por entorno (Vercel → Settings → Environment Variables). Vercel distingue Production, Preview y Development. Ahí decides si preview usa el mismo backend que producción o uno aparte (siguiente punto).
  5. (Muy recomendable) Un segundo proyecto de Supabase para pruebas. Créalo igual que el de producción, aplícale las mismas migraciones y pobla la carta con pnpm seed apuntando a él. En Vercel, las variables Preview apuntan a ese proyecto de pruebas; las Production al de verdad. Ventaja: puedes romper, borrar y reimportar sin miedo, y ningún experimento toca los datos reales ni el login real.

# 1. Partes de main, siempre actualizado

11.4. Qué pasa exactamente al fusionar a main

git push a una rama  ─────────►  Vercel: build de PREVIEW
                                 URL propia, aislada. Producción intacta.

Pull Request  (rama → main)  ─►  Vercel: build de PREVIEW del PR
                                 (última comprobación antes de mezclar)

Merge del PR a main  ─────────►  Vercel: build de PRODUCTION
                                 - instala dependencias
                                 - ejecuta  pnpm build   (tsc -b + vite build)
                                 - si el build falla, NO publica (producción sigue como estaba)
                                 - si va bien, cambia el dominio real al nuevo resultado
                                   de forma atómica (sin "web a medias")

11.5. La base de datos en este flujo

El código se despliega solo; el esquema de la base de datos no. Los cambios de BD siguen siendo migraciones que tú aplicas. Recomendación con el segundo proyecto de Supabase:

  1. Escribes la nueva migración (supabase/migrations/…_loquesea.sql) en tu rama.
  2. La aplicas al proyecto de pruebas: supabase link --project-ref <ref-staging> y luego supabase db push (o pegando el SQL en el editor del panel de Supabase de pruebas).
  3. Pruebas la mejora completa (código + BD) en la URL de preview / staging.
  4. Cuando fusionas a main, aplicas la misma migración al proyecto de producción (supabase link al ref de producción + db push). Hazlo justo antes o justo después del merge, según si el código nuevo necesita la columna nueva para funcionar.

Regla práctica para no romper producción: haz migraciones «aditivas» (añadir tabla/columna que el código viejo ignora). Primero aplicas la migración, luego despliegas el código que la usa. Evita en producción borrar o renombrar columnas en el mismo paso que cambias el código.

11.6. ¿Un solo Supabase para todo? Se puede, con matices

Si prefieres no mantener dos proyectos de Supabase al principio, puedes usar el mismo para preview y producción. Es asumible porque solo hay dos cuentas y RLS protege los datos. Pero ten en cuenta:

  • Cualquier prueba desde una URL de preview escribe en la carta real.
  • Las migraciones afectan a la web en vivo en el momento de aplicarlas (hazlo en horario de poco tráfico).
  • Nunca ejecutes pnpm seed contra ese proyecto: borraría la carta gestionada desde el panel.
  • Añade a Redirect URLs de Supabase también las URLs de preview que uses para poder hacer login desde ellas (o al menos la de staging.tudominio.es si fijas ese subdominio).

11.7. Extras que te ahorran disgustos

  • Que un build roto nunca llegue a producción: ya lo tienes en parte (si pnpm build falla, Vercel no publica). Añade además una comprobación en GitHub (Actions) o en el propio build que ejecute pnpm lint y pnpm test:run, y protege la rama main para exigir que pase antes de poder fusionar.
  • Volver atrás en segundos: Vercel guarda todos los despliegues. Si una versión sale mala, en el panel eliges un despliegue anterior y «Promote to Production». El dominio real vuelve a esa versión al instante (la BD no se revierte sola: por eso, migraciones aditivas).
  • Proteger las URLs de preview: son públicas aunque poco adivinables. El panel ya está protegido por login + RLS, pero si quieres, Vercel permite poner contraseña o «Vercel Authentication» a los despliegues de preview.
  • Netlify / Cloudflare Pages hacen exactamente lo mismo con otros nombres: «Deploy Previews» / «Preview deployments» por rama y PR, y «Production branch» = main. La estrategia de este capítulo no cambia.
  • Nombres de rama: te vale con main (producción) + una rama por mejora. La rama fija staging es opcional; es cómoda si quieres una dirección de pruebas estable o acumular varias mejoras antes de pasarlas juntas a producción.
